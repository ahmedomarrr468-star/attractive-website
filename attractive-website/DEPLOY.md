# النشر والإعداد (Attractive)

## الهيكل الجديد
```
public/        ملفات الموقع (index/store/builder/admin.html + procable-data.js + logo.png)  ← هي اللي بتتعرض للزوار
api/           دوال السيرفر (Vercel Functions). الملفات اللي بتبدأ بـ _ مش بتتعرض كروابط
scripts/       extract-defaults.mjs  (بيولّد api/_defaults.js من public/procable-data.js)
tests/         الاختبارات (npm test)
vercel.json    security headers + outputDirectory
```
> أي ملف خارج `public/` (زي package.json والاختبارات) بقى مش متاح للزوار.

## 1) المتغيرات في Vercel (Settings → Environment Variables)
| المتغير | مطلوب | الوصف |
|---|---|---|
| `ADMIN_API_SECRET` | نعم | باسورد الأدمن. 32+ حرف عشوائي. **غيّره حالاً** (القديم `attractive2026` اتكشف) |
| `DATA_KEY` | نعم | نص عشوائي 32+ بيشفّر الحسابات والأوردرات. **يتحط مرة واحدة ومايتغيرش** |
| `GOOGLE_CLIENT_ID` | اختياري | قيمة احتياطية؛ يمكن إدخال Client ID من إعدادات لوحة الأدمن بعد إعداد Google Cloud |
| `GOOGLE_SHEETS_WEBHOOK_URL` | اختياري | رابط احتياطي لـ Apps Script؛ يمكن حفظ الرابط الأساسي من لوحة الأدمن المشفّر على السيرفر |
| `LEGACY_ADMIN_SECRET` | مؤقتاً | الباسورد القديم، لو غيّرته قبل أول استيراد للحسابات القديمة. امسحه بعد الاستيراد |
| `GOOGLE_KEEP_PASSWORD` | اختياري | `1` = اللي سجّل بباسورد وبعدين دخل بـ Google يحتفظ بالباسورد (الافتراضي بيلغيه، شوف الملاحظة تحت) |

⚠️ **لو الموقع شغال فعلاً وفيه بيانات اتسجلت من غير `DATA_KEY`:** البيانات دي مشفّرة بباسورد الأدمن اللي كان ساري وقتها. حط `DATA_KEY` = **نفس ذلك الباسورد** الأول، وبعدها بس غيّر `ADMIN_API_SECRET`. لو غيّرت الباسورد الأول البيانات هتبقى مش مقروءة.

أنشئ مخزن Blob: Vercel → Storage → Create → Blob → ربطه بالمشروع (بيضيف `BLOB_READ_WRITE_TOKEN` تلقائياً).

## 2) الرفع
ارفع محتوى المجلد كله (من غير `node_modules`) على GitHub أو Vercel، ثم **Redeploy**.

## 3) تفعيل تسجيل الدخول بـ Google
1. https://console.cloud.google.com → أنشئ Project.
2. APIs & Services → **OAuth consent screen** → External → اكتب اسم الموقع وإيميلك → Publish app.
3. Credentials → Create credentials → **OAuth client ID** → نوع **Web application**.
4. في **Authorized JavaScript origins** ضيف:
   - `https://دومينك.com` و `https://www.دومينك.com` (لو بتستخدمه)
   - مفيش داعي لـ Redirect URIs.
5. انسخ الـ **Client ID**، ثم ضعه في لوحة الأدمن → الإعدادات → تسجيل الدخول بحساب Google واحفظ. يمكن بدلاً من ذلك ضبط `GOOGLE_CLIENT_ID` في Vercel ثم Redeploy.
6. افتح الموقع → "تسجيل الدخول": يظهر زر Google. لو لم يُضبط المعرّف يظل تسجيل البريد وكلمة المرور متاحاً.

سلوك مهم: لو عميل سجّل قبل كده بإيميل وباسورد ثم دخل بـ Google بنفس الإيميل، الحساب بيتربط، **وبيتلغي الباسورد وكل الجلسات القديمة** (عشان لو حد سجّل بإيميل مش بتاعه مايفضلش معاه وصول). العميل يكمل بـ Google. لو مش عايز كده: `GOOGLE_KEEP_PASSWORD=1`.

## 4) أول تشغيل: افحص الآتي
- ادخل `/admin.html` بالباسورد الجديد.
- الحسابات القديمة: أول طلب بيستوردها (الباسورد المحفوظ كـ base64 بيتحول لـ hash)، وبعدها الملفات القديمة **بتتمسح تلقائياً** بعد التأكد إن كل إيميل اتنسخ. هتلاقي في Vercel → Logs سطر `legacy plaintext file removed`. بعدها امسح `LEGACY_ADMIN_SECRET`.
- **جرّب طلب بنفسك** (الأهم): ضيف منتج للسلة، افتح DevTools وغيّر أي سعر في `localStorage` (`attractive_cart`)، وأكمل الطلب. في لوحة الأدمن الطلب لازم يظهر بالسعر الصحيح وعليه علامة **"سعر مُصحَّح"**.
- جرّب كابل مخصص من الـ builder، وطلب بكوبون.
- أرسل رأياً تجريبياً من الصفحة الرئيسية، ثم وافق عليه من لوحة الإدارة وتأكد من ظهوره للزوار.
- رابط Google Sheets: من لوحة الأدمن → الإعدادات، احفظ رابط Web App من Apps Script (HTTPS وينتهي بـ `/exec`). يُحفظ مشفّراً على السيرفر ولا يدخل ضمن بيانات المتجر العامة. يظل `GOOGLE_SHEETS_WEBHOOK_URL` خياراً احتياطياً؛ إعداد لوحة الأدمن له الأولوية. اعتبر أي رابط قديم كان ضمن بيانات المتجر العامة مكشوفاً، وألغِه من Google Apps Script بعد التأكد من عمل الرابط الجديد.
- Paymob: انشر الموقع على Vercel مع Blob مربوطاً، ثم من لوحة الأدمن → الإعدادات أضف Public Key وSecret Key وHMAC Secret وIntegration ID من حساب Paymob بوضع الاختبار. فعّل البوابة واحفظ. اترك حقلي Secret وHMAC فارغين لاحقاً للاحتفاظ بالقيم المحفوظة. رابط استقبال إشعار الدفع هو `https://<دومين-الإنتاج>/api/paymob-webhook`؛ أضفه كـ Transaction Processed Callback / Notification URL في إعدادات تكامل الدفع على Paymob (دعم الإشعار يختلف بحسب نوع التكامل). يُعتمد تأكيد الدفع من إشعار الخادم الموقّع فقط؛ رابط الرجوع للمتصفح لا يؤكد الدفع. مفاتيح الإنتاج لا تستخدم قبل إنهاء اختبار الدفع وحساب Paymob الفعلي.
- أكواد كوبونات المتجر لم تعد تُرسل ضمن `/api/store` للزوار؛ لوحة الإدارة تحصل عليها بجلسة الأدمن، والتحقق من الكود يتم عبر `/api/coupon`.

## 5) حماية إضافية من لوحة Vercel (لازم بإيدك)
- Firewall → Rate Limiting: قاعدة على `/api/*` (مثلاً 60 طلب/دقيقة لكل IP) وقاعدة أشد على `/api/admin-login` و`/api/accounts` و`/api/coupon` و`/api/reviews`. الحماية اللي في الكود best-effort بس.
- Settings → Security: فعّل Attack Challenge Mode وقت الهجمات.

## 6) الاختبارات
```
npm install
npm test        # 97 اختبار: محرك الأسعار، توكن Google، الـ API كامل، وكود الواجهة الحقيقي
npm run extract-defaults   # بعد أي تعديل على DEFAULT_* في procable-data.js
```
الاختبار بيفشل لو `api/_defaults.js` مش متزامن مع `public/procable-data.js`.

## 7) اللي اتغيّر في السلوك (اعرفه قبل ما يسألك عميل)
- **الأسعار بيحسبها السيرفر.** لو الأدمن غيّر سعر والعميل سلته قديمة، الطلب بيتسجل بالسعر الجديد وبيتعلّم "سعر مُصحَّح".
- سلة كابل مخصص قديمة (من قبل التحديث) هترفض مرة واحدة برسالة "السلة قديمة" ويضيف الكابل من جديد. "إعادة الطلب" بتعيد حساب السعر من الكتالوج الحالي.
- مزايا العضو (شحن مجاني/خصم) بتتحسب من حسابه الحقيقي على السيرفر، ومعطّلة لو الأدمن عطّل `perksActive`.
- الأدمن بس بالـ token (انتهاء 8 ساعات). الباسورد في header `x-admin-secret` بطل مقبول.
- تسجيل الخروج بيلغي الجلسة على السيرفر.

## 8) نقاط معروفة لسه ما اتغيّرتش (قرارك)
1. تحديد المعدل في الكود best-effort لكل نسخة؛ فعّل Vercel Firewall خصوصاً لمسارات الدخول والتحقق من الكوبونات.
2. الحسابات كلها في ملف واحد: كويس لمئات/آلاف قليلة، ولو كبرت انقلها لقاعدة بيانات (Neon/Postgres).
3. بيانات المتجر العامة (`attractive-store-data.json`) غير مشفرة بالتصميم؛ تأكد إنها مفيهاش أسرار.
4. توجد ترويسة CSP دفاعية جزئية في `vercel.json` (منع object، وتقييد base/frame/form)، لكنها لا تقيّد مصادر السكربتات؛ الصفحات تعتمد على سكربتات inline وTailwind من CDN. لا تُعتبر حماية XSS مكتملة. للوصول إلى CSP صارمة: بناء Tailwind محلياً، نقل السكربتات والـ inline event handlers إلى ملفات خارجية، ثم تحديد `script-src` بمصادر موثوقة أو nonce/hash والتحقق من جميع الصفحات قبل فرض السياسة.
5. مسارات التحقق من المعدل في الكود best-effort لكل نسخة تشغيل. لازم إعداد Vercel Firewall كما هو موضح أعلاه، بما يشمل `api/paymob-status`.
